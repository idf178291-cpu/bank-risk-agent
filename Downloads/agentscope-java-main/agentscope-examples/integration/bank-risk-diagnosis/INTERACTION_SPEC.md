# 银行机构风险诊断智能体 — 交互模式设计规格书

## 核心设计问题

经过多轮迭代，我们遇到了一个根本矛盾：

- 系统提示里写"逐步确认" → Agent 问得太频繁，用户嫌烦
- 系统提示里写"一次输出" → Agent 自己干完，用户无法参与
- 系统提示写"不要逐个文件调 ask_user" → LLM 不听

**根因**：用自然语言在系统提示里约束 LLM 行为是不可靠的。需要从架构层面定义"什么决策由 Agent 做，什么决策由用户做"。

---

## 设计原则

### 原则 1：区分信息展示和决策请求

| 类型 | 谁处理 | 需要 ask_user？ |
|------|--------|-----------------|
| 文件解析结果 | Agent 展示 | 不需要 |
| 问题提取结果 | Agent 展示 | 不需要 |
| 风险分类结果 | Agent 展示 | 不需要 |
| 选取分析方向 | **用户** | 需要 |
| 判断风险严重程度 | Agent 建议 + **用户**确认 | 需要 |
| 补充更多信息 | **用户** | 需要 |
| 生成最终报告 | Agent 执行 | 不需要 |

**规则**：展示信息不需要 ask_user。只有需要用户做出**不可逆选择**时才调用。

### 原则 2：Agent 负责分析，用户负责判断

```
Agent 的职责：                   用户的职责：
  阅读文档                        提供背景知识（Agent 不知道的）
  提取问题                        纠正 Agent 的判断偏差
  分类风险                        选择分析优先级
  识别模式                        做出风险管理决策
  生成建议                        审批最终报告
```

### 原则 3：信息密度要逐步提升

不要一开始就把所有分析结果抛给用户。先给概览，用户感兴趣再展开。

## 交互模型设计

### 三层交互模式

```
┌─────────────────────────────────────────┐
│ Layer 1: 自主层 (Agent 自行完成)         │
│  parse → 展示文件清单 → 加载知识库       │
│  提取问题 → 分类 → 生成摘要              │
│  **此层不调用 ask_user**                 │
├─────────────────────────────────────────┤
│ Layer 2: 概览层 (Agent 展示 + 用户决策)  │
│  展示：风险热力图 + TOP 3 主题 + 摘要   │
│  ask_user: "下一步想做什么？"            │
│  [深入某领域 | 补充文档 | 生成报告]      │
├─────────────────────────────────────────┤
│ Layer 3: 深入层 (用户驱动 + Agent 辅助) │
│  用户选定领域 → Agent 展开详细分析       │
│  Agent 识别信息缺口 → ask_user 补充      │
│  用户确认关键判断 → Agent 记录结论        │
│  生成报告                                │
└─────────────────────────────────────────┘
```

### 单次对话中的 ask_user 调用次数：最多 2-3 次

1. Layer 2 结束时：一次 multi_select（选方向）
2. Layer 3 中：可能一次 confirm（确认关键判断）
3. Layer 3 结束时：可能一次 confirm（确认生成报告）

## 具体交互流程

### 第 1 步：文档接收与解析（Agent 自主）

```
用户: "会话ID: xxx，请开始诊断"
Agent: 
  1. parse_documents(session_id="xxx")
  2. 复制 summaryTable 到消息
  3. 加载 issue_extract, risk_classify 两个核心 skill
  4. 开始提取问题（不暂停，不 ask_user）
```

### 第 2 步：问题提取与分类（Agent 自主）

```
Agent（连续输出，不暂停）:
  ### 📋 提取的风险问题
  
  | # | 问题 | 来源 | 类别 | 等级 |
  |---|------|------|------|------|
  | 1 | 贷后管理不到位 | 审计报告.docx | 信用风险 | 🟠HIGH |
  | 2 | 反洗钱身份识别缺失 | 监管意见.ofd | 合规风险 | 🔴CRITICAL |
  | ... | ... | ... | ... | ... |
  
  ### 📊 风险分布
  
  | 类别 | 问题数 | 严重/高 |
  |------|--------|---------|
  | 信用风险 | 8 | 3 |
  | 合规风险 | 5 | 2 |
  | ... | ... | ... |
```

### 第 3 步：概览确认与方向选择（用户决策点 #1）

```
Agent:
  综合来看，本次诊断发现 N 个风险问题，主要集中在信用风险和合规风险领域。
  
  [调用 ask_user]
  ui_type: "multi_select"
  question: "接下来您希望："
  options:
    - 深入信用风险（8个问题，3个严重/高风险）
    - 深入合规风险（5个问题，2个严重/高风险）
    - 深入操作风险（3个问题）
    - 补充更多文档
    - 直接生成完整报告
```

**这是对话中最重要的决策点。用户选择决定了后续深度。**

### 第 4 步：深入分析（用户驱动）

```
如果用户选了"深入信用风险":

Agent:
  好的，让我深入分析信用风险领域。
  
  ### 🔍 信用风险深度分析
  
  **TOP 主题 1：贷后管理薄弱（🔴严重）**
  - 涉及 5 个问题，来源于 3 份文档
  - 证据："抽查50笔贷款，12笔贷后检查间隔超90天" — 审计报告.docx
  - 证据："17笔贷款未按季开展贷后检查" — 风险排查报告.docx
  - 趋势：2023→2025 持续出现，未改善
  - 影响：涉及金额约 1.2 亿元
  
  **TOP 主题 2：授信集中度超标（🟠高风险）**
  ...
  
  **信息缺口**：缺少该银行 2025 年最新的信贷台账数据。
  是否需要补充上传？
  
  [调用 ask_user — 仅在发现信息缺口时]
  ui_type: "confirm"
  question: "缺少最新台账数据，是否补充？"
```

### 第 5 步：建议与报告（用户决策点 #2）

```
Agent:
  ### 💡 整改建议
  
  信用风险：
  1. [紧急] 建立贷后检查自动化提醒，明确检查频率和责任人（责任：信贷管理部）
  2. [短期] 对超期未检查贷款逐笔排查，15个工作日内完成（责任：各支行）
  ...
  
  [调用 ask_user]
  ui_type: "confirm"
  question: "是否基于以上分析生成完整诊断报告？"
```

## Agent 系统提示设计原则

### 不要用自然语言约束行为，要用结构化指令

❌ 差：`不要对每个文件单独评论`（LLM 可能忽略）
✅ 好：`parse_documents 返回 summaryTable，直接复制到消息。不添加任何评论。`

❌ 差：`要逐步引导用户`（太模糊）
✅ 好：`先输出问题清单+分类，再输出 TOP 3 主题+建议。全部输出完毕后调 ask_user。`

### 关键指令

```
1. parse_documents 后：复制 summaryTable -> 加载 issue_extract 和 
   risk_classify skill -> 开始提取问题。不暂停，不调 ask_user。

2. 分析完成后一次性输出：
   - 问题提取表（列出所有问题、来源、等级）
   - 风险分类分布表
   - TOP 3 重点风险主题（含证据来源）
   - 初步整改建议

3. 全部输出后调用 ask_user 1 次（multi_select），问用户下一步方向。

4. 根据用户选择展开深入分析或生成报告。

5. 仅在发现信息缺口或用户要求时，额外调用 ask_user。
   单次对话 ask_user 不超过 3 次。
```

## POC 实现要点

### 架构

```
用户 ←→ AG-UI SSE ←→ ReActAgent
                         ├── parse_documents (带 summaryTable)
                         ├── load_skill_through_path (知识库)
                         └── ask_user (仅 2-3 次/对话)
```

### 关键改动

1. **AgentConfig 系统提示**：按本 spec 重写，30 行以内
2. **parse_documents 工具**：返回 summaryTable（已实现）
3. **ask_user 调用次数**：Agent 内部计数，超过 3 次就报错（可选）
4. **删除**：每阶段确认的 ask_user

### 验证标准

| 场景 | 预期 ask_user 次数 |
|------|-------------------|
| 上传 5 文件 → 完整诊断 | 1-2 次 |
| 补充 2 文件 → 继续诊断 | 2-3 次 |
| 用户选"深入信用风险" | 1 次（仅在深入分析后） |

---

## 总结

本规格书定义了一个 **三层渐进交互模型**：

1. **自主层**：Agent 独立完成解析、提取、分类等机械性工作
2. **概览层**：Agent 展示全貌，用户选择方向
3. **深入层**：Agent 在用户选择的领域展开分析，识别信息缺口邀请用户补充

核心思想：**不是每步都确认，也不是全自动，而是在真正的决策点上让用户参与。**
