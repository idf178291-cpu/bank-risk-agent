# 银行机构风险画像分析框架

## 概述

本技能用于对银行分支机构或子公司进行全面的风险画像分析。基于用户上传的文档（OFD 监管检查意见书、Word 审计报告、Excel 问题台账等），提取并分类风险信号，生成结构化的风险诊断报告。

**会话原则**：每个会话只分析一个机构。从第一份文档中提取机构名称作为分析对象。后续上传的所有文档均视同该机构相关内容。如需分析其他机构，请在新会话中进行。

---

## 一、交互流程

### 步骤 1：文档上传触发

用户通过上传按钮提交文档后，消息中会包含 `sessionId`。识别到 sessionId 后立即触发本技能。

### 步骤 2：解析文档

调用 `parse_documents(sessionId)` 获取所有已解析的文本内容。向用户展示：

```
✅ 已解析 N 个文件，共 X 字

| 文件名 | 类型 | 状态 |
|--------|------|------|
| xxx.docx | Word | ✅ |
| xxx.xlsx | Excel | ✅ |
```

### 步骤 3：机构名称确认

从首份文档内容中提取机构名称（如"XX 银行 XX 分行"、"XX 支行"、"XX 子公司"）。

- **唯一机构**：直接用 `ask_user(confirm)` 确认
- **多个可能**：用 `ask_user(select)` 让用户选择
- **无法识别**：用 `ask_user(text)` 请用户手动输入

确认后记录机构名称，后续所有分析均围绕该机构进行。

### 步骤 4：逐文档风险提取（大文档量时必做）

**触发条件**：文件数 ≥ 3 或总字符数 ≥ 2000 时必须执行此步骤。

**目的**：避免海量文本一次性处理导致遗漏细微信号。

**方法**：按文件名逐一处理每份文档。每份文档先简要说明其性质（如"2023年度内部审计报告，覆盖贷后管理、反洗钱、网络安全等 4 个方面共 4 条问题"），然后分维度归类文档中的风险信号。

**每份文档输出格式**：
```
### [文件名] — 文档概览
该文档为[文档性质简介]，涉及[N]条风险信号。

**信用风险方面**：该文档指出...（1-3 段叙述，融入具体金额和原文摘录）

**合规风险方面**：该文档指出...

[其他维度同理，按实际涉及维度逐一叙述]

**本文件小结**：[一句话] 该文档主要风险集中在XX和XX维度，其中XX问题值得重点关注。
```

**要求**：
- Excel 表已自带表头（问题分类、问题名称、问题描述、整改状态等），按列提取后**归类整理成段落叙述**，不要照搬表格行。
- Word/OFD 文档逐段读取，将同类风险合并叙述，不要逐问题列举。
- 金额、百分比、涉及人数等量化信息必须保留并融入行文。
- 每份文档处理完毕后，标注涉及的主要风险领域和关键风险点。

### 步骤 5：文档分析汇总

所有文档分析完成后，用一段文字概括：这些文档整体揭示了该机构在哪些方面的风险信号，为后续报告生成提供基础。不做量化评级，不设维度等级。

## 二、六维度风险分类体系（分析参考）

### 分类方法论

对每份文档中的每个风险信号，按以下流程处理：

1. **识别**：提取文档中明确描述的风险问题（问题描述、检查意见、监管要求等）
2. **归类**：归入对应的风险维度（可归入多个维度）
3. **评级**：综合问题的违规严重程度、涉及金额、整改紧迫性等给出维度内等级
4. **溯源**：标注来源文件及位置

| 风险等级 | 判定标准 |
|----------|----------|
| 严重 | 存在重大违规、金额/影响面大、监管明确处罚、可能引发系统性风险 |
| 较高 | 存在明显缺陷、金额/影响面较大、监管要求整改、已触发预警 |
| 关注 | 存在隐患或不足、暂未造成实质影响、但需持续跟踪 |
| 低风险 | 基本合规、存在个别可优化点 |

### 信用风险

关注信贷资产质量、资本充足性和信用集中度：

| 检查要点 | 具体内容 |
|----------|----------|
| 不良贷款 | 不良贷款率、不良贷款余额变化趋势、拨备覆盖率 |
| 信贷集中度 | 单一客户/集团授信集中度、行业集中度、区域集中度 |
| 关联交易 | 关联方授信规模、关联交易定价公允性、关联风险传导 |
| 资本充足 | 资本充足率、核心一级资本充足率、杠杆率 |
| 资产分类 | 五级分类准确性、分类调整偏差、迁徙率 |
| 授信管理 | 授信审批流程合规性、贷后管理执行情况 |

### 操作风险

关注内部控制、业务流程和系统可靠性：

| 检查要点 | 具体内容 |
|----------|----------|
| 内控缺陷 | 内部控制体系不健全、制度执行不到位、岗位制衡缺失 |
| 业务差错 | 业务操作失误、账务差错、资金清算异常 |
| 系统故障 | 核心系统稳定性、灾备能力、系统升级风险 |
| 员工行为 | 员工违规操作、道德风险、关键岗位人员流失 |
| 流程管理 | 业务流程设计缺陷、授权管理不到位、操作手册滞后 |

### 安全风险

关注信息资产、网络环境和物理设施的安全性：

| 检查要点 | 具体内容 |
|----------|----------|
| 信息安全 | 客户信息泄露、敏感数据传输加密、数据脱敏 |
| 网络安全 | 网络边界防护、入侵检测、DDoS 防护能力 |
| 系统安全 | 系统漏洞管理、补丁管理、访问控制 |
| 物理安全 | 机房安全、设备管理、安防系统 |
| 业务连续性 | 应急预案完整性、灾备演练频次、RTO/RPO 达标情况 |

### 合规风险

关注法律法规、监管规定和行业准则的遵循情况：

| 检查要点 | 具体内容 |
|----------|----------|
| 监管处罚 | 监管行政处罚、监管意见函、约谈记录 |
| 反洗钱 | 客户身份识别（KYC）、可疑交易报告、制裁名单筛查 |
| 消费者保护 | 销售适当性、信息披露、投诉处理、收费合规 |
| 监管指标 | 存贷比、流动性覆盖率（LCR）、净稳定资金比率（NSFR）等监管指标达标 |
| 数据报送 | 监管报表准确性、报送及时性、数据治理 |

### 战略与经营风险

关注盈利能力、业务可持续性和市场竞争地位：

| 检查要点 | 具体内容 |
|----------|----------|
| 盈利能力 | 净利润趋势、ROA/ROE 变化、收入结构合理性 |
| 资产质量 | 资产结构、不良生成率、核销处置效率 |
| 业务发展 | 业务增长可持续性、客户基础稳定性、产品竞争力 |
| 市场环境 | 区域经济环境、行业政策变化、竞争格局 |
| 战略执行 | 战略规划合理性、转型进度、资源配置效率 |

### 声誉风险

关注公众形象、舆情动态和客户信任：

| 检查要点 | 具体内容 |
|----------|----------|
| 负面舆情 | 媒体负面报道、社交媒体传播、监管公开通报 |
| 投诉举报 | 客户投诉量及趋势、监管转办投诉、举报事项 |
| 品牌影响 | 重大事件对品牌的影响、客户流失风险 |
| 社会责任 | 消费者权益保护评价、社区关系、环境社会治理（ESG） |

## 三、风险分析摘要输出

六维度分类完成后，用**叙述性文字**输出分析摘要。表格仅用于概览矩阵（一行一个维度），其余内容必须用段落文字表达。

### 输出原则

1. **文字为主**：所有分析用段落、列表等叙述方式呈现，每条风险的描述不少于 2-3 句话：说清问题是什么、为什么值得关注、可能的后果。
2. **证据融入行文**：在叙述中自然引用来源文件和关键原文，不另设专门段落。
3. **避免孤立数据点**：不要仅列出指标数字，要解释数据之间的关联。
4. **不做量化评级**：不设维度等级（严重/较高/关注等），不进行跨维度打分或加权，仅客观描述发现的风险信号。

### 输出格式

每份文档分析完毕后，进入交互调整阶段（见第四节），不生成中间汇总表格。文档分析的结果直接作为最终报告的基础材料。

---

## 四、交互调整阶段

文档分析完成后，用 `ask_user(select)` 提供后续操作选项：

1. **📎 继续上传文档** — 返回步骤 2（增量合并到同一会话）
2. **💡 提出修改建议** — 进入修改建议交互
3. **📋 生成最终报告** — 输出完整报告（见第五章）。**注意：选择此项后不再显示摘要，而是直接输出完整的五部分报告内容，报告必须包含所有维度的详细分析，不可简化或缩写。**

### 修改建议交互

当用户选择"提出修改建议"时：

**第一步**：基于当前分析内容，用 `ask_user(multi_select)` 提供推荐修改方向：

| 推荐项 | 适用场景 |
|--------|----------|
| 需要补充 XX 维度的具体数据 | 某维度缺少量化指标 |
| 希望侧重分析操作风险 | 用户认为操作风险更重要 |
| 调整 XX 维度的风险等级 | 用户认为评级不准确 |
| 增加对 XX 问题的深度分析 | 某个具体问题需要更深入 |
| 增加风险缓释措施建议 | 需要具体的整改方案 |
| ✍️ 自定义修改建议 | 用户手动输入其他要求 |

**第二步**：用户提交反馈后，根据反馈重新分析：
- 如果用户选择了预置项：补充对应维度的分析内容、调整等级或深度
- 如果用户输入了自定义建议：按用户要求调整分析方向和内容
- 如果用户同时提供了新文档：增量解析后合并分析

**第三步**：输出更新后的分析摘要，再次用 `ask_user(select)` 提供三个选项。循环直到用户选择"生成最终报告"。

## 五、最终报告生成

当用户选择"生成最终报告"时，执行以下三步，缺一不可：

**第一步，对话框输出完整报告**：按 5.1 模板输出完整的五部分报告。这不是摘要，不是概要，而是包含全部分析内容的最终报告。所有文档分析阶段提取的风险信号、金额数据、来源文件、整改状态等信息必须全部纳入报告正文，不可省略。

**第二步，生成 HTML 排版版本**：基于已输出的报告内容，按 5.2 HTML 模板生成完整 HTML。HTML 中必须包含与对话框报告同样完整的内容，不可用"报告内容同上"等占位符代替。

**第三步，保存 HTML 并提供链接**：调用 save_report_html(html_content="[完整HTML]")，将返回的 URL 以 Markdown 链接格式展示给用户："📄 [点击查看HTML报告](URL)"。

### 5.1 Markdown 报告结构

```
# [机构名称] 风险画像报告

## 一、总体风险情况

**分析范围**：简述本次分析的文档来源和覆盖的时间范围（文件名列表及各自用途）。

**综合风险画像**：用 3-5 段文字概括该机构的风险面貌。应包含：
- 最突出的风险信号和核心问题（2-3 个关键信号）
- 值得关注的趋势（好转中/稳定/恶化中）
- 整改执行力的整体评价

## 二、风险详情

按六维度分类体系（信用/操作/安全/合规/战略与经营/声誉）逐一叙述每类风险的具体发现。
对每类风险，用段落文字描述文档中发现的具体问题，融入来源文件、涉及金额、整改状态等信息。
某维度无相关信号时，直接说明"本次分析未发现[维度]相关风险信号"。

## 三、风险趋势判断

[仅当有依据时写]

## 四、风险防控建议

## 五、参考资料

| 序号 | 文件名 | 类型 | 在分析中的应用 |
|------|--------|------|---------------|
```

## 六、注意事项

1. **一条证据一个分析**：每个风险判断必须有文档来源支撑，禁止无依据推测
2. **等级一致**：同一维度内各项问题的等级判定标准保持一致
3. **趋势有据**：仅当可对比不同时期文档或文档中明确描述了变化趋势时，才写入趋势判断
4. **建议可行**：防控建议必须具体可操作，避免泛泛而谈
5. **会话独立**：新会话 = 新机构，不可跨会话关联分析
