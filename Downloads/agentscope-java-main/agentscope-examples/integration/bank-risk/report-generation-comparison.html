INSTITUTION RISK PROFILING

提示词直出 · 交互式技能生成

同一份机构风险画像报告，两种生成模式。
提示词驱动直接生成 vs 当前项目交互式技能实现——
差异不在报告本身，而在报告是怎么来的。

1 本质差异：一步到位 vs 多步协作
📄

提示词驱动直接生成

把报告结构和分析方法论全部写在 system prompt 里，
用户上传文档后，LLM 一次性输出完整报告。

从输入到输出，中间没有停顿，
没有交互，没有纠偏机会。

🔍

交互式技能驱动生成

技能定义了多步骤交互流程：
上传→解析→逐文档提取→修改建议→最终报告+HTML 导出。

每一步都是用户可参与、可干预、可修正的，
报告是协作过程的产物，不是一次输出的结果。

2 同一个任务，两种流程

假设场景：上传大鹏银行东海分行 6 份文档（审计报告、问题台账、处罚决定书、检查通报等），生成机构风险画像报告。

📄 提示词直出模式

报告结构嵌在系统提示词里，用户提供输入，LLM 一次性输出

1 次 LLM 调用，0 次用户交互

↓
2

↓

❓ 报告生成了，但如果某个维度的分析不够深入？
❓ 如果漏掉了某个文档里的关键信号？
→ 只能重新描述需求，让 LLM 重新生成。

🔍 交互式技能模式（当前实现）

技能定义多步流程，每步可交互、可纠偏、可深挖

6-8 次 LLM 调用，用户多次参与

✓ HTML 报告可直接在浏览器打开查看

4 七个维度深度对比
维度 提示词直接生成 交互式技能生成
系统提示词 极长。必须包含完整的报告结构模板、六大维度方法论、分类体系、输出格式约束——全部写在 system prompt 里，每次对话都携带完整上下文 极短（10 行）。系统提示词只含角色 + 路由规则 + 交互规范。方法论和报告模板在 SKILL.md 里，按需加载
文档解析 依赖 LLM 自身能力读取文档文本，无专门的解析管道。合并单元格、多表结构等复杂 Excel 需要 LLM 自行理解 专用 Java 解析管道（POI + ZIP/XML），合并单元格填值、多表分隔标记。Java 层做信息保全，LLM 做语义理解
过程可见性 黑盒。用户输入 → 等待 → 报告出现。中间发生了什么，文档被怎么解读的，完全不可见 显式思考链。每份文档单独提取摘要 → 用户可逐份审视 → 不满意可提修改建议 → 最终报告有完整的追溯链条
用户参与 被动接收。报告的好坏完全取决于 prompt 写得多好和 LLM 当次表现。用户无法中途纠偏 主动引导。Agent 列出修改建议的推荐方向（多选），用户可以聚焦某个维度、增加深度分析、调整方向，甚至追加文档重新分析
信息覆盖率 取决于 LLM 单次理解能力。长文档可能被截断，多文档之间的交叉信号可能被遗漏。无法保证每份文件的每个信号都被提取 逐文档强制提取。技能要求大文档量时逐份处理，每份输出结构化摘要，最后交叉合并。每份文档的贡献可追溯
增量迭代 重置式。用户不满意需要重新描述需求 → LLM 重新生成整个报告。无法在已有分析基础上做增量修改 增量式。用户选择修改建议后 Agent 在原有分析基础上补充或调整，不需要从头生成。支持追加文档后合并分析
HTML 报告导出 可以要求 LLM 在回复末尾输出完整 HTML 代码块，用户手动复制保存为 .html 文件 Agent 生成 HTML 后调用 save_report_html 工具保存到服务端，返回可点击 URL，用户直接在浏览器中打开
5 如果要用提示词直出模式，需要把什么塞进 system prompt？
⚠️ 提示词直出模式的代价：当前项目中 institution_risk_profile/SKILL.md 的 290 行方法论全部需要嵌入 system prompt，加上报告模板和 HTML 模板，system prompt 将达到 3,000+ Token。每次对话都携带这些内容，不管用户当前是否在做机构画像分析。
需要嵌入的内容来源估算 Token
角色定义当前 SYS_PROMPT~50
六维度风险分类体系（信用/操作/安全/合规/战略/声誉——每类的检查要点和具体内容）SKILL.md 第二章~600
逐文档提取方法论（大文档量时的处理方式）SKILL.md 步骤 4~200
修改建议交互逻辑（推荐方向列表 + 循环处理规则）SKILL.md 第四章~250
Markdown 报告强制性子标题结构（1.1~1.6, 2.1~2.6, 3.1~3.2, 4.1~4.6）SKILL.md 第 5.1 节~350
HTML 报告模板（完整的 CSS + HTML 结构）SKILL.md 第 5.2 节~900
文件上传和解析指令需新增~200
交互规范（ask_user select 等）当前 SYS_PROMPT~100
合计~2,650 Token
对比：当前交互式模式的 system prompt 仅 ~400 Token（角色 + 路由 + 交互，10 行），其余知识全部在 SKILL.md 中按需通过 load_skill_through_path 加载。节省的 ~2,250 Token 在每次对话中都有效——不管当前任务是不是机构画像分析。
6 核心区别不是"能不能做"，而是"怎么做的"
提示词直出 交互式技能
本质Ask → Answer
用户给指令 → LLM 出报告		Ask → Parse → Extract → Review → Refine → Report
用户上传 → 解析 → 提取 → 审视 → 调整 → 报告
知识位置全部在 system prompt 中，每次对话必带在 SKILL.md 文件中，用时才加载
LLM 调用1 次大调用6-8 次小调用（每步独立）
失败成本高——重新生成整个报告低——重试失败的那一步即可
文档处理依赖 LLM 原生理解Java 管道预处理 + LLM 语义理解
输出一段 Markdown 文本Markdown 报告 + 可点击 HTML 链接
信任基础"我选择相信这份报告""我看到了每一步分析过程"
✓ 提示词直出适合：快速原型、非正式分析、文档量小的简单场景。"给我一份这个分行的风险画像"→几十秒出结果。

✓ 交互式技能适合：正式报告、多文档综合分析、需要审计追溯的严肃场景。每一步的用户参与不是"麻烦"，而是质量保证机制。
7 场景适配建议
场景推荐模式理由
快速预览、文档量小（1-2 份）提示词直出简单场景不需要多步交互，一次性生成即可
多文档综合分析（5+ 份）、文档量大交互式技能逐文档提取防止遗漏，增量调整避免重新生成
嵌入正式风险审批流程交互式技能每步可追溯，审批者能看到完整分析过程
需要向监管/审计提供分析依据交互式技能每份文档的提取结果独立可查，来源可回溯
非正式探索、验证分析框架提示词直出先用简单模式验证六维度分类是否合理，确认后固化为技能
需要生成排版可交付的 HTML 报告交互式技能save_report_html 工具返回可点击 URL，可直接发给客户或领导

从"生成报告"到"协作分析"

提示词直出模式让用户得到一份报告；
交互式技能模式让用户参与报告的形成过程。

在银行风控这类严肃场景中，
"报告可信"比"报告好看"更重要，
"过程可见"比"结果快速"更重要。

交互式技能不是让系统"更智能"，
而是把 AI 的分析能力拆解为可参与、可审视、可修正的步骤——
最终产出的是人机协作的、有据可依的、可交付的风险画像报告。
